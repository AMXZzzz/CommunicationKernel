# Services 目录划分

按**导航页**分组，找代码时先想「这是哪个页面的功能」。

| 目录 | 对应导航页 | 内容 |
|---|---|---|
| `Devices/` | 设备管理 | 设备配置存储、连接/断开、卡片视图拼装 |
| `Variables/` | 变量配置 | 变量存储、读写服务、后台轮询 |
| `Templates/` | 寄存器模板 | 模板库与模板引用展开 |
| `Logging/` | 通讯日志 | 环形日志缓冲、框架 ILogger 接入 |
| `Settings/` | 系统设置 | 端口、登录口令、反向代理、内网穿透（含 frpc 托管） |
| `Engine/` | 全部页面共用 | `EngineSession`：与 Hosting.App 的会话、健康轮询、状态流 |
| `Shell/` | 无（进程外壳） | 托盘图标、托盘日志窗、打开浏览器与局域网地址 |
| `Shared/` | 无（跨页工具） | 路径常量、运行时端口信息、纯展示辅助 |

## 命名空间不随目录变化

全部仍是 `CommunicationKernel.UI.WebMaster.Services`，**不加子命名空间**。

与 `Core.EngineRouter` 的约定一致（`Runtime/` 目录也用根命名空间）。
这样分目录纯粹是为了「找得到」，不引入任何 `using` 改动——
移动 22 个文件时代码零改动、零风险，将来再调整分组也一样。

想按目录改命名空间的话，须同时更新 `_Imports.razor` 与所有 `.cs` 的 using，
收益只是让 IDE0130 满意，代价是每次挪文件都要动一批引用。当前不做。

## 新增文件放哪

先问「操作员在哪个页面上用到它」：

- 只服务一个页面 → 放该页面的目录
- 多个页面都用，且与通讯会话有关 → `Engine/`
- 多个页面都用，是纯工具（路径、格式化、颜色）→ `Shared/`
- 与页面无关，属于进程本身（托盘、单实例、自启动）→ `Shell/`
